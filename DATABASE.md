# StudyHive database schema

The complete schema, dumped from the live PostgreSQL database on 2026-08-29 and checked against
§10 of `DOCS/StudyHive_Master_Project_Relay_Plan.html`. Everything below is what the database
actually contains, not what the entity classes hope it contains.

**This file is the schema reference.** `DOCS/database.md` is the *setup* guide — connection string,
Docker commands, migrations, backups. Different jobs; read that one to get a database running, this
one to understand what is in it.

**One migration, one DbContext.** All 23 tables live in `StudyHiveDbContext` and were created by the
single `20260820060329_InitialCreate` migration. S2, S3 and S4 do **not** need to create tables —
yours already exist. Add a migration only when you change your own entities.

---

## Verdict: the schema is sound. No changes needed before the S2 handoff.

Audited against the plan table by table, column by column, constraint by constraint. Every table,
column, index and constraint the plan asks for is present, and in several places the implementation
is stricter than the plan in ways that are worth keeping. Concretely:

**Correct per the plan.** All 23 tables (2 shared + 5 S1 + 6 S2 + 6 S3 + 4 S4). UUID primary keys
throughout, composite keys on the three genuine junction tables. `numeric(12,2)` for every money
column — no bare `decimal` anywhere. `timestamptz` for every instant. Every status column is
`varchar(N)` with a CHECK constraint. The named indexes from the plan all exist: `ix_br_student`,
`ix_br_status`, `ix_refresh_user`, `ix_rooms_search`, `ix_step_wf`, `uq_bri`, `uq_step`. The two
hard ones the plan calls out are both there and both work on a clean database: the partial unique
index `ux_wf_active` (one live workflow per request) and the `no_double_booking` GiST exclusion
constraint.

**Stronger than the plan, deliberately.** These are improvements, not drift — do not "simplify" them
away:

- **Generated columns** compute values instead of trusting callers to: `consumables.available_quantity`
  (`stock_quantity - reserved_quantity`), `quotations.total_amount`, `quotations.within_budget`,
  `quotation_line_items.line_total`, and the `slot` / `window` range columns. A generated column
  cannot drift from its inputs, which a trigger or application code can.
- **`chk_never_oversold`** on `consumables` (`reserved_quantity <= stock_quantity`). This is S3's
  no-oversell rule enforced by the database itself, so it holds even if the application logic has a
  race. S3 still has to write correct transactional code — but this is the backstop.
- **`citext`** on `users.email`, `suppliers.contact_email` and `email_notifications.to_email`, so
  `Alice@x.lk` and `alice@x.lk` collide instead of creating two accounts.
- **`tstzrange` + GiST** for `room_bookings.slot` and `maintenance_windows.window`, which is what
  makes the exclusion constraint and the availability query possible at all.
- **`chk_line_shape`** on `quotation_line_items`: a Room line must carry a `room_booking_id` and no
  `consumable_id`, and vice versa. A malformed line is rejected rather than stored.
- **Quotation versioning** (`uq_quote_version`, `ux_quote_active`) supports the revise-and-resubmit
  loop the plan's status list implies but never spells out.

**Two things to know, neither a defect.**

1. **`updated_at` is not maintained by a trigger.** Every editable table has it and it defaults to
   `now()` on insert, but nothing in the database updates it afterwards — the application does, in
   the controllers. That is fine while all writes go through the API, which is the design. But if
   you fix data with raw SQL in psql, `updated_at` will silently go stale. Set it yourself when you
   do that.
2. **`stock_reservations.status` is `Pending / Reserved / Released / Used`.** Some UI text describes
   this lifecycle as "held → confirmed → issued → released". The database is authoritative; the
   words on the screen are a label. S3: use the four values above, and do not add a fifth without a
   migration, because the CHECK constraint will reject it.

## Conventions that apply to every table

| Rule | How it shows up |
|---|---|
| Primary key | `id uuid`, generated by the application. Junction tables use a composite key instead. |
| Money | `numeric(12,2)`. Never bare `decimal` — EF Core would silently pick a store type. |
| Instants | `timestamptz`, default `now()`. Editable tables carry `created_at` and `updated_at`. |
| Status columns | `varchar(N)` + `CHECK (... IN (...))`, mapped in C# with `.HasConversion<string>()`. |
| Deletes | `RESTRICT` by default. `CASCADE` only on genuinely owned children. |
| Naming | Postgres `snake_case`, C# `PascalCase`, JSON `camelCase`. Configured once in `Program.cs`. |
| Deactivation | Rooms and consumables are never deleted, only `is_active = false`. |

Extensions required: `citext` and `btree_gist`. Both are created by the migration.

### Cascade map — what a delete actually does

`CASCADE` (owned children, deleted with their parent): `refresh_tokens` → `users`;
`booking_request_items` and `booking_request_equipment` → `booking_requests`;
`workflow_step_logs` → `workflow_executions`; `quotation_line_items` → `quotations`;
`room_equipment` and `maintenance_windows` → `study_rooms`;
`consumable_suppliers` → `consumables`; `stock_reservations` → `booking_request_items`.

`SET NULL` (history that outlives what it referenced): `audit_logs.user_id`,
`email_notifications.booking_request_id`, `stock_transactions.booking_request_id` and
`.stock_reservation_id`, `quotation_line_items.room_booking_id` and `.consumable_id`.

Everything else is `RESTRICT`. In particular a `student_profile`, a `booking_request`, a
`study_room` and a `consumable` cannot be deleted while anything points at them.

chain-of-thought, not raw prompts, not API keys. The assignment forbids persisting hidden reasoning,
and saying so is worth a mark.

## S2 — Rooms & Availability

### `study_rooms`
`id` uuid PK · `name` varchar(60) UNIQUE · `building` varchar(60) · `floor` int ·
`capacity` int CHECK > 0 · `hourly_rate` numeric(12,2) CHECK >= 0 · `qr_code` varchar(64) UNIQUE ·
`is_active` boolean · `created_at` / `updated_at`.
Index `ix_rooms_search (is_active, capacity)`.

### `equipment_types`
`id` uuid PK · `name` varchar(80) UNIQUE · `category` varchar(40) · `description` text ·
`is_active` boolean · `created_at` / `updated_at`.

A *type* ("Projector"), not a physical device. A room holds a quantity of each — which is why the
old many-to-many "equipment" table was dropped: it implied one projector installed in two rooms.

### `room_equipment`
Composite PK `(room_id, equipment_type_id)` · `quantity` int default 1 CHECK > 0 · `installed_at`.
`room_id` CASCADE, `equipment_type_id` RESTRICT.

### `booking_request_equipment`
Composite PK `(booking_request_id, equipment_type_id)` · `quantity_required` int default 1 CHECK > 0.
`booking_request_id` CASCADE, `equipment_type_id` RESTRICT.

### `maintenance_windows`
`id` uuid PK · `room_id` → `study_rooms` CASCADE · `starts_at` / `ends_at` timestamptz
CHECK `ends_at > starts_at` · `reason` text · `created_at` ·
`window` **tstzrange generated** as `tstzrange(starts_at, ends_at, '[)')`.
GiST index `ix_mw_room (room_id, window)` — this is what lets the availability query exclude
rooms under maintenance without a row-by-row scan.

### `room_bookings`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `room_id` | uuid | → `study_rooms`, RESTRICT |
| `booking_request_id` | uuid | → `booking_requests`, RESTRICT |
| `starts_at` / `ends_at` | timestamptz | CHECK `ends_at > starts_at` |
| `checked_in_at` | timestamptz | set by the QR check-in (M-14) |
| `status` | varchar(20) | CHECK: Confirmed, Cancelled, Completed, NoShow |
| `slot` | tstzrange | **generated** from starts_at/ends_at |
| `created_at` / `updated_at` | timestamptz | |

```sql
ALTER TABLE room_bookings ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (room_id WITH =, slot WITH &&) WHERE (status = 'Confirmed');
```

**The most important constraint in the database.** Two confirmed bookings cannot overlap in the same
room — enforced by PostgreSQL, inside whatever transaction attempts it. Application-level checking
cannot give you this under concurrency. It is the last line of defence inside S4's approval
transaction, and S2 should be able to explain it out loud.

## S3 — Consumables & Stock

### `consumables`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `name` | varchar(120) | UNIQUE |
| `description` | text | |
| `unit` | varchar(20) | |
| `unit_price` | numeric(12,2) | CHECK >= 0 |
| `stock_quantity` | int | default 0, CHECK >= 0 |
| `reserved_quantity` | int | default 0, CHECK >= 0 |
| `available_quantity` | int | **generated**: `stock_quantity - reserved_quantity` |
| `min_stock_level` | int | default 0, CHECK >= 0 |
| `is_active` | boolean | default true |
| `created_at` / `updated_at` | timestamptz | |

`CONSTRAINT chk_never_oversold CHECK (reserved_quantity <= stock_quantity)` — the database refuses
to be oversold. Partial index `ix_cons_low (is_active) WHERE stock_quantity <= min_stock_level`
makes the low-stock screen (W-21) cheap.

Never write to `available_quantity`; it is computed. Move `stock_quantity` and `reserved_quantity`.

### `suppliers`
`id` uuid PK · `name` varchar(120) UNIQUE · `contact_email` citext · `phone` varchar(30) ·
`address` text · `is_active` boolean · `created_at` / `updated_at`.

### `consumable_suppliers`
Composite PK `(consumable_id, supplier_id)` · `supply_price` numeric(12,2) CHECK >= 0 ·
`is_preferred` boolean default false · `created_at` / `updated_at`.
Partial unique `ux_preferred (consumable_id) WHERE is_preferred` — at most one preferred supplier
per consumable.

### `stock_reservations`
`id` uuid PK · `booking_request_item_id` UNIQUE → CASCADE · `consumable_id` → RESTRICT ·
`quantity` int CHECK > 0 · `status` varchar(20) CHECK **`Pending`, `Reserved`, `Released`, `Used`** ·
`reserved_at` / `released_at` / `used_at` / `created_at` / `updated_at`.
Index `ix_res_cons (consumable_id, status)`.

The unique constraint on `booking_request_item_id` means one reservation per request line — a
retry cannot silently double-reserve.

### `stock_transactions`
`id` uuid PK · `consumable_id` → RESTRICT · `transaction_type` varchar(20) CHECK
`StockIn`/`StockOut`/`Reserve`/`Release`/`Adjust` · `quantity` int CHECK `<> 0` ·
`balance_after` int · `booking_request_id` SET NULL · `stock_reservation_id` SET NULL ·
`notes` text · `created_by` → `users` RESTRICT · `created_at`.
Index `ix_tx_cons (consumable_id, created_at DESC)`.

Append-only ledger. `quantity <> 0` rather than `> 0` because a StockOut is negative.

### `email_notifications`
`id` uuid PK · `to_email` citext · `template` varchar(50) · `subject` varchar(200) ·
`booking_request_id` SET NULL · `status` varchar(20) CHECK Queued/Sent/Failed/DeadLettered ·
`attempt_count` int default 0 · `max_attempts` int default 3 · `next_attempt_at` timestamptz ·
`provider_message_id` varchar(200) · `last_error` text · `sent_at` · `created_at`.
Index `ix_email_due (status, next_attempt_at)`.

An outbox with retry and a dead-letter state, not fire-and-forget.

## S4 — Costing, Validation, Approval & Audit

### `quotations`
| Column | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `booking_request_id` | uuid | → `booking_requests`, RESTRICT |
| `version` | int | default 1 |
| `room_fee` | numeric(12,2) | CHECK >= 0 |
| `consumable_cost` | numeric(12,2) | CHECK >= 0 |
| `total_amount` | numeric(12,2) | **generated**: `room_fee + consumable_cost` |
| `budget_snapshot` | numeric(12,2) | the budget as it was when quoted |
| `within_budget` | boolean | **generated**: `total <= budget_snapshot` |
| `currency` | char(3) | default `LKR` |
| `status` | varchar(20) | CHECK: Draft, Proposed, Approved, Rejected, Superseded |
| `created_at` / `updated_at` | timestamptz | |

Unique `uq_quote_version (booking_request_id, version)`. Partial unique
`ux_quote_active (booking_request_id) WHERE status IN ('Proposed','Approved')` — a request can have
a history of quotations but only one live one.

`budget_snapshot` is copied, not joined, so an approved quotation still shows the budget it was
judged against even if the student later edits the request.

### `quotation_line_items`
`id` uuid PK · `quotation_id` CASCADE · `item_type` varchar(20) CHECK `Room`/`Consumable` ·
`room_booking_id` SET NULL · `consumable_id` SET NULL · `item_name` varchar(150) ·
`quantity` numeric(10,2) CHECK > 0 · `unit_price` numeric(12,2) CHECK >= 0 ·
`line_total` numeric(12,2) **generated**: `quantity * unit_price` · `created_at`.

```sql
CONSTRAINT chk_line_shape CHECK (
  (item_type = 'Room'       AND room_booking_id IS NOT NULL AND consumable_id  IS NULL) OR
  (item_type = 'Consumable' AND consumable_id  IS NOT NULL AND room_booking_id IS NULL))
```

A Room line points at a booking, a Consumable line points at a consumable, and neither can point at
both or at nothing.

### `approval_decisions`
`id` uuid PK · `quotation_id` → RESTRICT · `decided_by` → `users` RESTRICT ·
`decided_by_role` varchar(20) · `decision` varchar(20) CHECK
`Approved`/`Rejected`/`RevisionRequested` · `comments` text · `decided_at`.
Index `ix_ad_quote (quotation_id, decided_at DESC)`.

`decided_by_role` is stored alongside the user id on purpose: it records the role held *at the time
of the decision*, which survives a later role change.

### `audit_logs`
`id` uuid PK · `user_id` SET NULL · `correlation_id` uuid · `action` varchar(60) ·
`entity_type` varchar(60) · `entity_id` uuid · `details` jsonb · `ip_address` varchar(45) ·
`created_at`.
Indexes `ix_audit_entity (entity_type, entity_id)`, `ix_audit_user (user_id, created_at DESC)`.

Append-only — there is deliberately no update or delete path. `user_id` is SET NULL so the audit
trail outlives a deleted account. `ip_address` is 45 characters to fit IPv6.

## Two design decisions people try to undo

**1. Eligibility is computed, never counted.** There is no `current_week_bookings` column, and there
should not be — a counter has no defined week boundary and nothing to reset it. Eligibility is a
query, and `ix_br_student` makes it cheap. The rule lives in
`api/src/StudyHive.Api/Services/BookingEligibilityService.cs`: active, not suspended, fewer than 3
penalty points, and under `max_bookings_per_week` for the current Asia/Colombo week.

**2. `booking_requests` has no column pointing at `workflow_executions`.** The reference goes one
way only, from workflow to request. The old spec had foreign keys in both directions, which EF Core
cannot order when inserting. To find the current workflow, query `workflow_executions` by
`booking_request_id` — `ux_wf_active` guarantees at most one live row.

## Moving to Neon instead of Docker

Yes — migrations, export and import all work against Neon. The plan already names Neon as the hosted
database (§13), and nothing in the schema is Docker-specific.

### 1. Put the connection string in `.env`

Copy [`.env.example`](.env.example) to `.env` and fill in the Neon values. `.env` is gitignored;
`.env.example` is the tracked template.

Neon shows a URL, but Npgsql wants key=value form — translate it:

```
Neon shows:   postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require
Npgsql wants: Host=HOST;Database=DBNAME;Username=USER;Password=PASSWORD;SSL Mode=Require;Trust Server Certificate=true
```

`SSL Mode=Require` is not optional — Neon refuses plaintext connections.

### 2. Create the schema on Neon

The migration builds all 23 tables from empty. Point the connection string at Neon and run it:

```bash
set -a && source .env && set +a
```

```bash
dotnet ef database update --project api/src/StudyHive.Api --startup-project api/src/StudyHive.Api
```

**One thing to check first.** The migration creates the `citext` and `btree_gist` extensions. Neon
supports both, but they must be creatable by your role — if `CREATE EXTENSION` is refused, create
them once in the Neon SQL editor as the owner:

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

`btree_gist` is not optional: without it the `no_double_booking` exclusion constraint cannot be
created, and that constraint is what makes overlapping bookings impossible.

### 3. Or copy your existing local data across

Schema and data together:

```bash
docker exec studyhive-db pg_dump -U studyhive -d studyhive --no-owner --no-privileges > studyhive.sql
```

```bash
psql "postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require" -f studyhive.sql
```

`--no-owner --no-privileges` matters: the dump would otherwise reference the local `studyhive` role,
which does not exist on Neon, and every `ALTER ... OWNER TO` would fail.

Schema only (then let the app seed, or start clean):

```bash
docker exec studyhive-db pg_dump -U studyhive -d studyhive --schema-only --no-owner --no-privileges > schema.sql
```

Data only, if the schema is already migrated:

```bash
docker exec studyhive-db pg_dump -U studyhive -d studyhive --data-only --no-owner > data.sql
```

### 4. Do not carry the dev accounts to a real environment

`DevDataSeeder` only runs when the environment is Development, so a production API will not create
them. But if you copy a full dump from your local database, the dev users come with it — including
the password published in this repository. Either restore schema-only, or delete them afterwards:

```sql
DELETE FROM users WHERE email LIKE '%@studyhive.dev';
```

Their booking requests and workflows cascade or restrict accordingly; check what remains before
deleting on anything you care about.

### 5. What changes in the app

Nothing in the code. `Program.cs` reads `ConnectionStrings:Default` and `ConnectionStrings__Default`
from the environment overrides it, so no committed file needs editing. Outside Development the API
already fails startup if the connection string, JWT signing key, agent key or `AllowedHosts` are
missing — so a half-configured deployment stops rather than silently falling back to development
values.

Keep `docker-compose.yml` for local work. Neon and Docker are not exclusive: developers can stay on
the container while deployed environments use Neon.
